# Korean Policy / Research Report Writing

발주처에 제출하는 한국어 정책·연구 보고서를 작성·수정·검증할 때 따르는 규칙. 학술논문이 아니라 정책 메시지를 전달하는 문서를 전제로 함.

응답은 한국어로 하되, 변수명·계량 라벨·코드·파일경로 등 기술 문자열은 영어로 유지함.

---

## 0. 이 스킬을 쓰는 시점

- 발주처용 한국어 보고서 초안, 수정, 최종본 검증 작업
- 정책 시사점을 포함한 산업·경제·경영·기술 분석 보고서
- HWP/HWPX/DOCX 기반 보고서이고 PDF 제출이 동반되는 경우
- 코멘트(검토자 의견)를 반영해 본문·표·그림을 함께 수정하는 작업

쓰지 않는 시점:
- 학술 저널 논문 초안 — `academic-paper-writing` 스킬 사용
- 단순 요약·번역·교정만 요청된 경우
- 발주처 양식(쪽수 한도, 표지 양식)이 핵심 이슈인 경우 — 양식 파일에 의존

---

## 1. 전체 작성 원칙

보고서는 분석 결과를 나열하는 문서가 아니라, 독자가 바로 판단할 수 있는 정책·전략 메시지를 전달하는 문서임.

- 핵심 결론을 먼저 제시하고, 그 뒤에 분석 근거를 붙임.
- 통계적으로 중요한 결과라도 보고서 주제와 연결되지 않으면 본문 중심에 두지 않음.
- 방법론 설명은 생략하지 않되, 독자가 왜 그 방법이 필요한지 이해할 수 있게 풀어 씀.
- 표와 그림은 독자가 본문 없이도 의미를 이해할 수 있도록 제목, 주, 해석 문장을 함께 정리함.
- 새로운 분석·수정이 들어가면 본문 논리, 표 번호, 숫자, 그림, 참고문헌, PDF 디자인까지 함께 검증함.
- 보고서 안에는 작업 과정, 파일명, 내부 판단, 코멘트 처리 내역을 쓰지 않음.

---

## 2. 작성·수정 워크플로우

대규모 수정일수록 한 번에 많이 바꾸기보다 섹션별로 수정하고, 각 섹션마다 숫자와 문체를 확인함.

1. 코멘트와 메모를 모두 수집함.
2. 코멘트를 주제별로 분류함.
3. 반영 계획을 먼저 작성함 (사용자에게 계획을 보여준 뒤 실행).
4. 계획이 보고서 목적, 분석 결과, 양식과 맞는지 검증함.
5. 본문을 수정함.
6. 표, 그림, 수식, 주석, 참고문헌을 함께 수정함.
7. 숫자와 문장 해석이 일치하는지 검증함.
8. 파일 무결성(HWPX의 경우 ZIP 구조, 메모 잔존 여부)을 확인함.
9. PDF로 내보내 디자인을 확인함.
10. 최종적으로 전체 문서의 논리 흐름을 다시 읽음.

---

## 3. 요약(Executive Summary) 작성 원칙

요약은 보고서의 가장 중요한 정책 메시지를 먼저 보여주는 공간임.

- 분석 방법 소개보다 정책·전략 시사점을 앞세움.
- "무엇을 분석했는가"보다 "그래서 무엇을 해야 하는가"가 먼저 보여야 함.
- 학술적 표현은 줄이고, 보도자료로 옮겨도 어색하지 않은 문장으로 정리함.
- 통계 결과는 핵심 숫자만 남기고, 정책적 의미를 같이 붙임.
- 한 문단 안에 분석·정책·사례를 뒤섞지 않음.
- 종결 방식은 발주처·양식에 맞추되, 같은 문서 안에서는 일관되게 유지함.

좋은 요약의 구조:

1. 문제 상황과 보고서의 핵심 메시지
2. 가장 중요한 분석 결과
3. 기업(또는 현장) 전략 관점의 시사점
4. 정부 정책 관점의 시사점
5. 보고서가 제안하는 실행 방향

---

## 4. 보고서 문체 원칙

본문은 연구자의 내부 작업 기록이 아니라 완결된 설명이어야 함.

피해야 할 표현 (작업 로그 흔적):

- "코멘트를 반영함", "수정 완료", "검증함", "저장해둠"
- "보조검토로 위치시킴", "재현분석 결과"
- "해석:"처럼 메모식 표지
- 파일명, 원자료 파일명, 작업 폴더명
- 독자에게 거친 내부 라벨 (예: `3NN`, `5NN`, `IPW`, 임시 변수 코드)
- 문서 내 통일되지 않은 약어

대체 표현:

- `추가 강건성 분석`
- `첨부`
- `민감도 점검`
- `분석 결과는 다음과 같음`
- `본문에서는 ...에 초점을 둠`
- `이 결과는 ...을 시사함`

기타 원칙:

- 독자가 모르는 약어는 처음에 풀어 쓰고 이후 용어를 통일함.
- 너무 짧은 단문이 연속되면 앞뒤 문장과 통합함.
- 하나의 bullet이 지나치게 길면 의미 단위로 나눔.
- 양식이 요구하는 종결형을 따르되, 같은 계위에서는 같은 문체를 유지함.

---

## 5. 문단·bullet 계위

정책 보고서의 bullet 계위는 발주처 양식을 우선시하되, 일반적 한국 정부·국책연구원 양식은 다음 구조를 따름.

- 큰 주장 / 정책 메시지: `□`
- 세부 설명·근거·분석 결과: `○`
- 하위 근거·예시·세부 방법: `-`

주의사항:

- `□` 다음에 바로 `-`가 오지 않게 함.
- `□`는 하나의 큰 판단을 담음. `○`는 그 판단의 근거·해석을 담음.
- bullet 하나가 반 페이지 가까이 길어지면 반드시 나눔.
- 같은 계위의 bullet은 같은 문체와 비슷한 길이를 유지함.

사용자 지정 세부 규칙(엄수):

- `□`는 제목 성격이므로 **짧게** 씀(한 줄, 명사형 소제목 권장). 긴 문장은 `□`에 두지 않고 `○`로 내림.
- `□` 하나에는 `○`가 **최소 두 개** 들어가야 함. `○` 하나만 달리는 `□`는 만들지 않음.
- `-`(찍은)는 세부 내용이며 **없어도 됨**(필요할 때만 사용).
- `○`는 **두 줄을 넘지 않게** 함. 길면 의미 단위로 나누거나 `-`로 내림.
- 들여쓰기: `○`는 **앞 스페이스 두 칸**(`  ○ `), `-`는 **앞 스페이스 네 칸**(`    - `)으로 맞추고, 같은 계위는 들여쓰기를 일관되게 유지함.
- 종결은 보고서체 명사형(예: `~제시함`, `~필요함`, `~구성함`)으로 통일함.

---

## 6. 논리 흐름 점검

보고서 전체는 다음 흐름이 자연스러워야 함.

1. 왜 이 주제가 중요한가
2. 기존 논의의 한계는 무엇인가
3. 본 보고서는 어떤 질문을 던지는가
4. 어떤 데이터와 방법으로 검증하는가
5. 핵심 결과는 무엇인가
6. 결과가 가설 또는 주장과 어떻게 연결되는가
7. 기업과 정책에 어떤 의미가 있는가
8. 한계와 후속 검증은 무엇인가

검토할 때는 각 섹션 첫 문장만 읽어도 전체 주장이 이어지는지 확인함. 중요한 표 앞에는 반드시 "이 표가 무엇을 판단하는지"를 먼저 설명함.

---

## 7. 분석 결과 서술 원칙

분석 결과는 "유의하다/유의하지 않다"에서 끝나면 부족함.

- 계수의 방향, 크기, 유의수준을 함께 제시함.
- 결과가 어떤 가설·주장을 지지하는지 명확히 씀.
- 가설이 부분적으로만 지지되면 그 범위를 분명히 함.
- 사양별 결과가 다를 때는 가장 신뢰할 사양을 메인으로 정하고, 나머지는 첨부·민감도 점검으로 정리함.
- 유의하지 않은 결과를 억지로 긍정적으로 해석하지 않음.
- 본문 결론은 메인 사양 기준으로 쓰고, 보조 사양은 결과의 안정성 또는 한계로 설명함.

좋은 문장 구조:

- `<표 n>의 (x)열에서 핵심 계수는 ...로 나타나며, 이는 ...을 의미함.`
- `따라서 H1은 ... 범위에서 지지됨.`
- `다만 ... 사양에서는 효과가 약해지므로, 결과는 ...로 해석함.`
- `이 결과는 단순한 ...보다 ...가 중요하다는 본문 논리와 정합적임.`

---

## 8. 방법론 설명 원칙

방법론은 독자가 왜 필요한지 이해할 수 있게 풀어 써야 함.

- 통계 기법을 단순 나열하지 말고, 어떤 문제(선택편의, 내생성, 결측 등)를 해결하기 위한 절차인지 설명함.
- 공변량, 추정 방식, 고정효과, 표준오차, 결측 처리는 표 주석 또는 방법론 문단에 구체적으로 남김.
- 전문용어를 쓰더라도 독자가 따라올 수 있게 한 문장 설명을 붙임.
- 결과가 잘 나오는 사양만 고르는 방식은 피함. 공변량 균형, 표본 손실, 해석 가능성, 본문 논리와의 정합성을 함께 봄.
- 본문에는 메인 사양 하나를 정해 쓰고, 나머지는 첨부 또는 민감도 점검으로 둠.
- 내부 분석 라벨(`3NN`, `5NN` 등)은 보고서에 그대로 쓰지 않고 "3-최근접 이웃 매칭"처럼 풀어 씀.

방법론 문단에 포함할 표준 항목:

- 처리변수 / 종속변수
- 분석 단위 (관측치 정의)
- 식별전략 또는 추정 방식
- 사용 공변량
- 고정효과 / 시간 차원
- 표준오차 산정 방식
- 결측 처리 방식
- 표본 크기 / 표본 구성
- 결과 해석 기준

---

## 9. 결측치 처리 설명 원칙

결측치 처리는 분석 신뢰성과 직결되므로 보고서에 숨기지 않음.

- 어떤 변수가 결측이 많은지 설명함.
- 결측을 단순 제거하면 표본이 얼마나 줄어드는지 설명함.
- 왜 대체가 필요한지 설명함.
- 어떤 방식으로 대체했는지 구체적으로 씀.
- 결측 여부 더미를 포함했는지 밝힘.
- 결측 처리 방식이 결과를 과도하게 만들지 않았는지 민감도 점검을 제시함.
- 본문에는 핵심만 쓰고, 세부 민감도 결과는 첨부로 보낼 수 있음.

---

## 10. 가설과 결과 연결 원칙

각 가설은 표의 어느 열과 어떤 계수로 판단하는지 분명해야 함.

가설 판단 문장에 포함할 요소:

- 표 번호
- 열 번호
- 핵심 변수명
- 계수와 유의수준
- 지지 여부
- 해석의 범위

주의사항:

- 한 사양에서만 유의한 결과는 "확정적 결론"이 아니라 "부분적 근거"로 다룸.
- 분리 추정과 공동 추정을 직접 우열 비교처럼 쓰지 않음.
- 통제변수 추가로 결과가 달라질 때는 어떤 통제변수가 왜 필요한지 먼저 설명함.
- 기존 사양과 새 사양이 공존하면 독자가 헷갈리므로, 본문 메인 사양을 하나로 정리함.

---

## 11. 정량 지표 정성 설명 원칙

정량 지표는 독자가 실제 상황을 떠올릴 수 있게 풀어 설명함.

- 지표의 정의(어떻게 계산되는지)를 한 문장으로 씀.
- 값이 높을 때와 낮을 때 각각 무엇을 의미하는지 씀.
- 극단값의 한계(너무 높으면 / 너무 낮으면 무엇이 문제인지)를 씀.
- 본문 주장과 연결되는 직관을 산업·현장 사례로 한두 줄 풀어 씀.

---

## 12. 표 작성 원칙

표는 논문식 형식을 따르되 정책 보고서 독자가 읽을 수 있어야 함.

- 표 번호는 `<표 1>`, `<표 2>`처럼 순차적으로 붙임.
- "보조표"라고 쓰지 않고, 필요한 경우 첨부의 정식 표로 번호를 부여함.
- 표 제목은 표가 무엇을 판단하는지 드러나야 함.
- 표 앞에는 표의 목적을 설명하는 문단을 둠.
- 계수, 표준오차, 유의수준 표기를 일관되게 함.
- `* p<0.10`, `** p<0.05`, `*** p<0.01` 주석을 넣음.
- 통제변수는 가능하면 표 안에 계수까지 제시함. `Controls: Yes`만 두기보다 주요 통제변수의 계수와 표준오차를 표 안에 제시하는 편이 더 투명함.
- 변수명이 본문에서 영어로 제시된 경우, 표에서도 동일 표기를 사용함 (예: `priorAlliance`, `PostMna`). 본문 중 변수명은 필요 시 이탤릭으로 일반 명사와 구분함.
- 표가 너무 작아지면 열을 줄이거나 표를 나누되, 본문 논리를 해치지 않게 함.

배치·쪽 나눔 규칙(엄수):

- 모든 표는 그 표를 설명하는 본문 문단 **뒤에** 배치함. 본문에 언급이 없으면 직전 문단 끝에 `(<표 N> 참조)`를 붙임. 같은 문단에 여러 참조가 붙으면 `(<표 N>, <그림 M> 참조)`로 병합함.
- 언급 존재 여부를 검사할 때 `표 1`이 `표 10`·`표 11`에 부분 매칭되지 않게 숫자 경계를 확인함.
- 쪽(장)을 넘는 긴 표는 잘려도 되지만, **글자처럼 취급을 해제해야** 나뉨. HWPX 기준: `hp:tbl`에 `treatAsChar="0"` + `textWrap="TOP_AND_BOTTOM"` + `pageBreak="CELL"` + `repeatHeader="1"`, 그리고 머리행 셀(`hp:tc`)에 `header="1"`. 셀에 `header="1"`을 빠뜨리면 repeatHeader가 있어도 다음 쪽에 머리행이 반복되지 않음.
- 표 캡션 문단은 keepWithNext를 켜서 표와 같은 쪽에 묶음(캡션만 쪽 하단에 남는 고아 캡션 방지).

글꼴 기준:

- 표 제목: 11pt 수준
- 표 내용: 10pt 수준 (10pt 미만은 PDF에서 읽기 어려움)
- 같은 계위의 표는 같은 글꼴 크기 유지

---

## 13. 그림 작성 원칙

그림은 개념도와 추정결과 그림의 역할을 구분해야 함.

- 개념도는 분석 프레임워크와 관계 구조를 보여줌.
- 추정계수 기반 그림은 실제 결과의 형태(예: 역U자, 한계효과 곡선)를 보여줌.
- 선, 글자, 범례가 겹치지 않아야 함.
- 그림 제목과 축 제목은 짧고 명확해야 함.
- 그림이 페이지 경계나 본문 텍스트와 겹치지 않는지 PDF로 확인함.
- 그림은 "예쁜 장식"이 아니라 본문 주장에 직접 기여해야 함.
- 모든 그림은 그 그림을 설명하는 본문 문단 **뒤에** 배치함. 언급이 없으면 직전 문단 끝에 `(<그림 N> 참조)`를 붙임(표 규칙과 동일).
- 그림 캡션 문단은 keepWithNext를 켜서 그림과 같은 쪽에 묶음.

---

## 14. 사례·인용 원칙

사례는 분석 결과를 설명하는 보조 근거이지, 계량분석 결과처럼 쓰면 안 됨.

- 사례가 데이터셋 분석 결과인지, 정책적 적용 사례인지 명확히 구분함.
- 특정 국가·산업 사례를 "별도 표본 회귀 결과"인 것처럼 쓰지 않음.
- 보도자료나 기업 발표를 활용할 때는 APA 등 표준 스타일에 맞춰 참고문헌을 정리함.
- 사례는 너무 많이 넣지 않고, 보고서 논리를 보여주는 대표 사례만 사용함.
- 데이터에 없는 사실을 분석 결과처럼 말하지 않음.
- 사례 범위를 명시함 (예: "본 보고서 결과를 ...에 적용해 보는 참고 사례임").

---

## 15. 정책 시사점 작성 원칙

정책 시사점은 기업 관점과 정부 관점을 분리해 씀.

기업·현장 관점:

- 분석 결과에서 직접 도출되는 실행 옵션을 제시함.
- 구체적 의사결정 단위(시점, 규모, 단계)로 풀어 씀.
- 단순 명제가 아니라 어떤 조건에서 어떤 선택을 해야 하는지 씀.

정부 정책 관점:

- 단순 자금·세제 지원을 넘어 제도·계약·정보·인력 같은 패키지 설계를 제안함.
- 보도자료 활용을 고려해 통계 용어를 줄이고 메시지를 단순화함.
- 분석 범위를 넘는 정책 주장은 자제하고, 범위를 명시함.

---

## 16. 본문과 첨부 구분

본문은 핵심 분석과 결론을 담고, 첨부는 민감도 점검과 보완 분석을 담음.

- 메인 분석은 본문에 둠.
- 강건성 분석, 대안 추정, 민감도 점검은 첨부에 둘 수 있음.
- 본문에서는 첨부 결과를 "추가 확인" 또는 "민감도 점검"으로 언급함.
- 본문 결론이 첨부 결과에 의해 흔들리면 해석을 조정함.
- 첨부 표도 본문 표와 같은 양식으로 정리함. 첨부라고 표 주석·변수명·글꼴을 대충 처리하지 않음.

---

## 17. 수정 표시 원칙 (검토자에게 보내는 버전)

검토 단계에서 신규 내용은 검토자가 한눈에 알 수 있어야 함.

- 원칙적으로 신규 내용은 빨간색으로 표시함.
- 문장 일부만 수정한 경우 전체 문장을 빨갛게 하기보다 수정된 표현만 빨갛게 표시함.
- 대규모 문단 교체는 문단 전체를 빨갛게 할 수 있으나, 최종본 전환 전에 표시 범위를 정리해야 함.
- 표 안에 새로 들어간 숫자·주석도 빨간색 표시 대상임.
- 기존 문장과 새 문장이 자연스럽게 어우러지는지 확인함.

## 18. HWPX/HWP 작업 원칙

HWPX는 ZIP 기반 XML 문서이므로 구조 무결성이 중요함. HWP 바이너리도 동일 원칙 적용.

- 수정 전 반드시 백업을 만듦.
- 사용자가 파일을 열어둔 상태에서는 저장 충돌 가능성이 있으므로 가능하면 닫은 뒤 수정함.
- 수정 후 ZIP/파일 무결성을 확인함.
- 검토 단계 메모 필드가 최종본에 남아 있지 않은지 확인함.
- 표 번호, 이미지 참조, 문단 스타일, 글꼴 크기가 깨지지 않았는지 확인함.
- HWP COM(또는 한컴오피스)으로 열어서 손상 경고가 없는지 확인함.
- PDF로 내보내 실제 렌더링을 확인함.

무결성 체크 항목:

- 파일이 정상적으로 열리는가
- ZIP 엔트리 오류가 없는가 (HWPX)
- `Contents/section0.xml` 파싱이 되는가 (HWPX)
- 메모 필드가 남아 있지 않은가
- 이미지 파일이 누락되지 않았는가
- 표와 그림 번호가 순차적인가
- 빨간색 수정 표시가 필요한 곳에 남아 있는가 (검토본의 경우)

발주처 양식(HWP) 파일에 맞춰 재조판할 때(엄수):

- 양식 HWP를 한컴 COM으로 HWPX로 변환한 뒤 header.xml의 명명 스타일(예: KIET `K_` 스타일셋)의 charPr/paraPr/borderFill **ID를 그대로 참조**해 본문을 생성함. 새 paraPr 추가는 개조식 들여쓰기 등 양식에 없는 계층에만 최소로 함.
- 글꼴·크기·자간·장평·줄간격·들여쓰기·여백·쪽번호 위치는 양식 XML의 수치를 실측해 쓰고, 눈대중으로 만들지 않음.
- 각주는 괄호 텍스트가 아니라 **실제 각주 개체**(`hp:footNote` + `hp:autoNum`, secPr의 `footNotePr` 번호형식)로 넣고, 변환 후 각주 번호·하단 구분선·본문 위첨자 위치를 PDF에서 확인함.
- 섹션을 삭제·추가하면 header.xml의 `secCnt`, `content.hpf`(manifest·spine), `META-INF/container.rdf`를 **모두 일치**시켜야 함. 하나라도 참조가 어긋나면 한컴이 파일 열기를 거부함(오류 메시지 없이 Open이 False를 반환).
- header.xml에 charPr/paraPr를 추가할 때 한컴은 참조(`paraPrIDRef` 등)를 **id 속성이 아니라 목록의 순번(0-based 위치)** 으로 해석함. 새 항목은 반드시 목록 끝에 id 오름차순으로 붙여 **id == 순번**을 유지해야 함. 중간 순서가 어긋나면 열리기는 하지만 엉뚱한 문단모양(예: 캡션용 가운데 정렬)이 적용됨.
- 표 캡션은 별도 문단보다 표 개체 안의 `<hp:caption side="TOP">`으로 부착하는 편이 안전함 — 표가 다음 쪽으로 밀려도 캡션이 함께 이동해 고아 캡션이 원천 차단됨(한컴이 스키마를 정상 수용, 위치는 outMargin과 inMargin 사이).
- 숫자(`14,500`)가 줄 경계에서 갈라지면 오독 위험이 있으므로, 일반 문단은 `breakLatinWord="KEEP_WORD"`로 두고 URL·CPC 코드열 등 **긴 라틴 연속열(약 16자 초과)이 있는 문단만** `BREAK_WORD` 문단모양을 쓰는 이원화가 필요함. 자동 부가하는 참조구는 `(<표 N> 참조)`의 공백을 NBSP로 넣어 분리를 막음.
- 한컴은 COM으로 열어 저장할 때 문단을 재조판하므로 lineseg는 근사값이면 충분함. 실제 줄바꿈은 paraPr의 `breakSetting`이 지배함.
- 개조식 본문·긴 CPC 코드·URL·파일경로가 있는 문단은 `breakLatinWord`와 `breakNonLatinWord`를 **모두 `BREAK_WORD`(글자 단위)** 로 함. `KEEP_WORD`(어절 유지)는 양쪽정렬과 만나면 긴 토큰이 한 줄을 통째로 차지하며 낱글자 자간으로 벌어지고, 라틴 `HYPHENATION`은 URL 도메인 중간에 하이픈을 삽입해(예: `wip-o.int`) 주소를 오독하게 만듦.
- 렌더링 PDF의 글꼴 목록을 확인함: 대상 글꼴(KoPub 등)이 설치되지 않은 PC에서는 한컴이 대체 글꼴로 PDF를 만들므로, 양식 준수 여부는 파일의 fontRef가 양식과 동일한지로 판단하고, 대체 렌더링 사실을 산출물 설명에 남김.
- PowerShell에서 `[기본과제]…`처럼 대괄호가 든 파일명은 와일드카드로 해석되어 복사·이동이 조용히 실패함 — 반드시 `-LiteralPath`를 사용함.

## 19. PDF 디자인 검증 원칙

HWPX/DOCX 화면에서 괜찮아 보여도 PDF에서 깨질 수 있으므로 반드시 PDF로 확인함.

- 모든 페이지가 비어 있지 않은지
- 표가 페이지 밖으로 나가지 않는지
- 표 안 글자가 너무 작지 않은지 (10pt 미만이면 의심)
- 그림의 글자와 선이 겹치지 않는지
- 수식 줄바꿈이 어색하지 않은지
- 제목, 표 제목, 본문, 주석의 글꼴 크기가 계위별로 일정한지
- 장별 첫 페이지와 표·그림이 많은 페이지를 따로 확인
- footer/header에 placeholder가 남아 있지 않은지

특히 확인할 페이지:

- 요약 페이지
- 방법론 설명 페이지
- 메인 분석 표 페이지
- 핵심 그림 페이지
- 정책 시사점 페이지
- 첨부 시작 페이지
- 참고문헌 페이지

---

## 20. 숫자 검증 원칙

보고서 숫자는 표, 본문, 주석, 그림이 모두 일치해야 함.

- 본문 계수와 표 계수가 같은지
- 유의수준 별표와 p값이 맞는지
- 합산·계산값(total effect, marginal effect 등)이 원 계수와 일치하는지
- 표본 수, 관측치 수, 매칭 표본 수가 앞뒤로 다르지 않은지
- turning point 등 계산값은 원 계수로 다시 계산해 검증
- 그림에 사용한 값이 표와 같은지
- 첨부 표가 본문 결론과 충돌하지 않는지
- 오래된 분석 결과 숫자가 본문에 남아 있지 않은지 (이전 사양의 잔존 숫자 검색)

검증 후 명시적으로 보고:

- `표와 본문 숫자가 일치함.`
- `구 표본 또는 이전 사양의 숫자가 본문에 남아 있지 않음.`
- `본문 결론은 메인 사양 기준으로 작성되어 있음.`

## 21. 금지 토큰 체크리스트

최종본 직전에는 아래 작업 흔적·내부 라벨이 남아 있지 않은지 검색함. 프로젝트 고유 토큰은 별도로 추가함.

작업 메모 흔적:

- 코멘트
- 메모
- 반영 완료
- 수정 작업
- 저장
- 재현분석
- 보조검토
- 보조표
- 원문 표
- 해석:
- 미지지
- 검증해
- 작업

내부 파일·라벨 흔적:

- `analysis_outputs`, `data_clean` 등 내부 폴더명
- 원자료 파일명, 임시 변수명
- 매칭 라벨(`3NN`, `5NN`, `IPW` 등)을 풀어 쓰지 않은 채 노출

검토자 고유명도 본문에서 제거함 (예: 검토자 박사·교수의 이름). 단, 방법론상 반드시 필요한 용어라면 독자 친화적인 표현으로 바꿔 씀.

## 22. 최종 검증 체크리스트

최종 제출 전 최소한 다음 항목을 확인함.

- 제목이 최신 제목과 일치함.
- 요약이 정책 메시지 중심으로 쓰였음.
- 보고서 본문에 내부 코멘트 처리 표현이 없음.
- 모든 표 번호가 순차적임.
- 모든 그림 번호가 순차적임.
- 본문에서 언급한 표와 실제 표 번호가 일치함.
- 표 앞에 표의 목적 설명이 있음.
- 표 안 글꼴이 읽을 수 있는 크기임 (10pt 이상).
- 수식 줄바꿈이 자연스러움.
- 변수명이 본문과 표에서 일치함.
- 통제변수가 표 주석 또는 표 안에 명확히 제시됨.
- 결측치 처리 방식이 설명되어 있음.
- 메인 분석과 첨부 분석의 역할이 구분되어 있음.
- 사례가 분석 결과처럼 과장되지 않았음.
- 참고문헌과 본문 인용이 연결되어 있음.
- HWPX/DOCX가 정상적으로 열림.
- PDF가 정상적으로 생성됨.
- PDF에서 겹침, 잘림, 빈 페이지가 없음.
- 숫자, 계수, 유의수준, 표본 수가 일치함.
- 최종 파일에 메모 필드가 남아 있지 않음.

## 23. 마지막 읽기 기준

최종본은 다음 질문에 모두 답할 수 있어야 함. 막히는 부분이 있으면, 그 부분은 아직 수정이 필요한 부분임.

- 이 보고서의 한 문장 메시지는 무엇인가?
- 독자는 요약만 읽어도 정책 방향을 이해할 수 있는가?
- 표와 그림은 본문 주장에 꼭 필요한가?
- 분석 방법은 신뢰할 수 있게 설명되어 있는가?
- 숫자는 앞뒤로 맞는가?
- 사례는 과장되지 않았는가?
- 첨부와 본문의 역할이 분명한가?
- 보고서 안에 작업자의 흔적이 남아 있지 않은가?
- PDF로 봤을 때 제출용 문서처럼 보이는가?
